# LIBERO-PRO 适配计划

重点是把“针对旧任务、修复一次”的流程，改成“根据当前任务生成技能序列、在各阶段持续检查并修复”的闭环。现有 VLA、cuRobo 和关节轨迹执行可以继续复用。

## 1. 先统一任务身份，保证整条链跑的是同一个 PRO case

现在只切换评测的 `task_suite_name` 还不够，`diagnose_failed.py` 和 `tta_repair_batch.py` 仍有 LIBERO-plus 的任务解析逻辑。PRO 的 swap/task 与原任务可能同名，容易在诊断或修复时跑回原任务。

让 baseline、census、诊断和 repair 显式传递同一套 suite、task、BDDL、初始状态索引、seed 和实际指令，并检查实际导入的 LIBERO 路径。当前 PRO benchmark 已经支持从 BDDL 读取真实指令，这部分保留并确认 T5 缓存与实际输入一致。

## 2. 将当前任务的技能计划与检索到的 demo 分开

当前阶段序列主要来自旧 memory 的 task/demo。swap 可能仍能沿用任务逻辑，但 task 扰动改变目标物体或目标关系后，旧序列就可能不适用。

应先根据当前任务确定 `PhaseSpec` 序列，再为每个阶段独立检索记忆。例如当前需要 `Pick(pan)`，可以借用其他任务的抓取经验，但不继承那个 demo 后续的任务顺序。第一版可以先为 PRO 任务准备核验过的阶段序列。

## 3. memory 改成按技能选择参照物的相对位姿

Pick 使用当前目标物体的坐标系，将记忆中的 ready pose 变换到当前场景。已有 `PointCloudSelector` 可以复用，目标物体从 `phase.arguments` 获取，不再依赖命令行固定的 `--item`。初次修复和后续阶段切换都要接入这套检索方式。

Place 则应以目的地或容器为参照，并补偿当前抓持姿态与演示的差异。现有 Place memory 需要按当前构库代码重建，再接入携物规划。TurnOn、Open、Close 分别明确使用 VLA、专用控制或对应技能记忆。

## 4. 把一次性 repair 接成可重复干预的阶段闭环

当前 repair 只接管一次，oracle 路径也没有启用完整的后续阶段续接。需要让阶段 runtime 独立运行：进入阶段、必要时对齐、交给 VLA、检查结果，再决定推进或修复当前阶段。

先做“每个 Pick 前对齐”的实验，验证双 Pick 任务的第二次抓取也能恢复，再接按失败触发的修复。每次交回 VLA 时清理旧动作队列，用最新观测重新推理。

保留 `census → diagnose → t* → prefix 回放` 作为离线实验入口，但首次干预之后要根据新轨迹判断后续阶段。对于 `TurnOn → Pick`，先完成开灶台，再在 Pick 前对齐，不能开局就跳过前置操作。

## 5. 修正超时推进和技能完成判定

当前超时也会推进阶段，协调器随后可能把 Pick 当作成功并更新持物状态。应明确区分：确认成功才推进并更新状态；失败或超时进入修复、重试或结束；前置条件已经满足时，经确认后跳过。

Place 目前主要判断“松手”，需要补充物体是否到达目标位置并稳定下来。TurnOn 要处理“原本已经打开”的情况。优先验证未抓住、放错位置和前置条件已满足这些情况，避免错误状态传到后续阶段。

## 6. 闭环跑稳后，再迁移训练和扩大评测

先比较 baseline、单次 Pick 对齐、多阶段 Pick 对齐和加入 Place 后的效果，再扩展到其他 PRO 扰动。使用相同 case 对照，同时记录任务成功率、阶段结果、实际干预次数和总执行步数。

稳定产生完整成功轨迹后，再验证 SFT/DPO。采集时保留 phase、干预编号、动作来源和连续时间索引，不直接沿用已经出现退化的修复动作切片训练方式。

第一个验收点：在一个双 Pick 任务中，不手工指定目标物体，系统能够依次绑定两个正确目标、分别完成对齐，并检查两次抓放结果。
