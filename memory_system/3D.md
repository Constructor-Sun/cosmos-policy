# Memory System 3D 基础与后续 Skill Check 路线

本文记录仍然有效的 RGB-D/3D 基础，以及清理旧 Phase / Feasible 状态机后准备实现的 3D Skill Check 边界。

## 1. 总体原则

正式运行逻辑只允许依赖未来真实系统可获得的信息：

```text
RGB-D + camera parameters + robot state
                  -> runtime 3D logic

simulator object state / predicate / segmentation
                  -> test oracle only
```

LIBERO object state、predicate 和 instance segmentation 可以用于生成测试真值，但不能进入被测试的 runtime 路径。

## 2. 已验证的几何基础

### Stage 1：Metric Depth

状态：已完成。

已验证从 LIBERO depth observation 到米制 depth 的转换、depth observation 接线，以及 canonical image/render image 的 pixel flip 约定。详细测试和结果位于 `tests/stage1_depth/README.md`。

### Stage 2：目标可见表面 3D 几何

状态：已完成。

当前验证量是目标物体可见表面的 camera-frame Z-depth：

- runtime 输入为 RGB-D 与给定目标区域；
- Oracle 使用 MuJoCo `mj_ray()`；
- 在 eroded object mask 上逐像素比较；
- 覆盖 LIBERO-10 中 Pick、PlaceIn、PlaceOn、TurnOn、Close 涉及的可测对象。

已有结果：总体 median of medians 约 `1.15 mm`，median of P90 约 `4.01 mm`。除 `microwave_1` 的 P90 异常约 `182 mm`、需要单独复核外，其余按对象统计均通过。详细实现和结果位于 `tests/stage2_geometry/README.md`。

这些结果只说明 RGB-D 几何链可用，不等于已经定义了可靠的 skill 完成规则。

## 3. 已停止的旧实验路线

原文档曾记录 Phase3D、Feasible3D、Completion 和 recovery 串联实验。该路线依赖：

- `PhaseVerifier` / `Phase3DVerifier`；
- `FeasibleVerifier` / `Feasible3DVerifier`；
- `ExecutionMonitor` 多阶段状态机；
- Phase/Feasible recovery selector；
- 旧 `skill_completion` 实现。

这些在线模块已经从当前代码删除，不再作为未来设计约束。旧实验记录仍可从 Git 历史恢复，但不继续保留在当前主文档中，避免把已放弃的状态机误认为现行架构。

`memory_system/offline/` 和既有 artifact 保持不变；本次清理不代表否定其中的数据，也不提前决定未来 Skill Check 的 memory schema。

## 4. 下一阶段：按 skill 实现 3D Skill Check

下一阶段不恢复统一的 Phase/Feasible gate，而是针对每种 skill 明确定义“动作是否已经完成”。建议的统一输入边界为：

```text
SkillCheckInput
  - current SkillStep: skill + arguments
  - RGB-D / camera parameters
  - robot EE pose / joint state / gripper state
  - 由感知获得的具体 item / target 几何
  - 必要的短时历史

SkillCheckResult
  - complete: bool
  - confidence / evidence
  - reason
  - object-relative measurements
```

这里先表达稳定的数据边界，不在清理阶段创建空类或占位 runtime。

### Pick

需要区分“夹爪闭合”和“目标物体确实随夹爪建立并保持抓取关系”。测试覆盖 LIBERO-10 中不同抓取对象，Oracle 可使用 simulator grasp/predicate，但 runtime 只能使用 RGB-D、夹爪和机器人状态。

### PlaceIn / PlaceOn

需要以具体 item 与 target 的相对几何判断放置关系，并区分刚进入区域、稳定放置和已释放。`PlaceIn` 与 `PlaceOn` 不应只共享一个距离阈值。

### Open / Close / TurnOn

需要针对带关节或状态变化的目标定义观测证据。Simulator joint/predicate 只作为测试 Oracle；runtime 规则应由视觉几何、目标跟踪和机器人状态构成。

## 5. 与 planner continuation 的关系

未来主通路建议保持单向、可观测的状态转移：

```text
planner current SkillStep
-> optional object-relative alignment
-> policy execution
-> skill-specific 3D Skill Check
   -> incomplete: continue policy or invoke explicit recovery decision
   -> complete: planner advances to next SkillStep
-> next-skill alignment / execution
```

Skill Check 只回答当前 skill 是否完成；是否继续、重新对齐、重新规划或恢复，由更上层 orchestrator 决定。这样可以避免重新形成一个隐式耦合的 Phase/Feasible/Completion 状态机。

## 6. 建议实施顺序

1. 先定义只读的 `SkillCheckInput` / `SkillCheckResult` 数据契约和 planner step identity；
2. 从一个边界最清晰的 skill 开始，实现单独 checker 与 training-demo replay 测试；
3. 测试覆盖单位使用 `task × skill step × item/target`，同时报告预测、Oracle 和差异；
4. checker 稳定后再接入 Eval，但先保持 observation-only；
5. 再实现 planner continuation；
6. 最后增加 object-relative alignment、replan 和 recovery 决策。

每一步都应先固定输入、输出和通过条件，不让新的判断逻辑直接侵入 Initial Alignment。

## 7. 当前不做

- 不实现 RealSense、ROS、ZED 等真机 adapter；
- 不在本次清理中设计新的 artifact 格式；
- 不把 simulator object state 引入 runtime；
- 不复活 Phase/Feasible 开关或 legacy compatibility stub；
- 不在尚未验证 checker 前连接自动 planner advance/recovery。
