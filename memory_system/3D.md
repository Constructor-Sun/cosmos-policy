# Memory System 3D 扩展计划

## 1. 目标

在不改变当前 2D baseline 的前提下，为 Memory System 增加可靠的 RGB-D/3D 信息。首先确认 3D 信息本身正确，再分别讨论 Phase、Feasible、Skill Completion 和 Recovery 如何使用 3D。

当前阶段只面向 LIBERO/MuJoCo 验证，不实现真机传感器。设计上要求正式运行逻辑只依赖 RGB-D、相机参数和机器人本体状态，不读取 simulator object state。

## 2. 当前不做的内容

- 不实现 RealSense、ROS、ZED 等真机传感器或 adapter；
- 不讨论 Sim Memory 直接迁移到 Real；
- 不预先确定 Phase、Feasible、Completion 和 Recovery 的具体 3D 规则；
- 不测试或设计 depth confidence；
- 不为一次实验同时修改多个判断阶段。

## 3. 测试边界

模拟器状态可以作为测试 Oracle，但不能进入被测试对象：

```text
LIBERO RGB-D + Robot State
            -> 被测试的 Memory System

LIBERO Object State / Predicate / Segmentation
            -> Test Oracle
            -> 只用于生成真值和判断测试是否通过
```

测试必须保证：

- 正式 3D 计算路径只接收未来真实系统也能够提供的信息；
- object state、simulator predicate 和 instance segmentation 只出现在测试代码中；
- 每个测试只回答一个明确问题，不附带无关测量。

## 4. 分阶段执行

每个阶段必须先明确被测试对象、测试目的和通过条件。当前阶段通过后，才能进入下一阶段。

### Stage 1：Depth 正确性

目的：确认从 LIBERO RGB-D observation 得到的米制 depth 正确。

测试：在相同 camera、pixel 和 simulator state 下，比较 RGB-D 计算结果与 simulator Oracle 的 depth。

本阶段只测试 depth 差异，不测试 Phase、目标识别、时序稳定性或置信度。

当前状态：已完成。米制转换、depth observation 接线和 canonical/render pixel flip 约定已验证，详细实现与结果见 `tests/stage1_depth/README.md`。

### Stage 2：目标 3D 几何正确性

目的：确认给定目标区域后，RGB-D 得到的目标 3D 几何正确。

测试范围：覆盖 LIBERO-10 中所有 SkillStep 涉及的不同 item、target 和 region。比较 RGB-D 结果与 simulator Oracle 中相同定义的目标几何。

在实现前必须先明确被比较的几何定义，例如可见表面中心、目标点或目标区域；不能默认使用 simulator object center 代替 RGB-D 实际估计的量。

本阶段不让 3D 结果参与在线判断和纠正。

当前状态：已完成。

已确认定义：物体可见表面 camera-frame Z-depth；Oracle 使用 MuJoCo `mj_ray()`，逐像素比较 eroded object mask 上的深度误差。

结果：libero_10 全部 10 个 task，Pick/PlaceIn/PlaceOn/TurnOn/Close 的可测物体已测量。总体 median of medians ≈ 1.15 mm，median of P90 ≈ 4.01 mm；除 `microwave_1` 的 P90 异常（≈ 182 mm，需单独确认）外，其余 by-object 均 PASS。详细实现与结果见 `tests/stage2_geometry/README.md`。

### Stage 3：Phase 3D

当前状态：已完成（Pick 第一版）。

目的：在 Pick 从开始到首次进入 Feasible 区域的全过程中，持续判断夹爪是否正常接近当前目标。进入 Feasible 区域是 Phase 的唯一正常结束条件；在此之前发生夹爪状态改变属于 Phase Error。

#### 3D 目标与距离

当前 Phase Memory 指定目标区域；在线 template match 得到当前 mask；RGB-D 将 mask 内有效深度恢复为世界坐标点，生成 `TargetGeometry.center_xyz_world`。Pick 第一版使用 mask 内有效 3D 点的逐坐标 median 作为代表点。

当前距离为：

```text
d(t) = ||eef_xyz(t) - target_xyz(t)||
```

Phase 不在第一次距离减小时结束，而是持续到首次进入 Feasible 区域。

#### Phase 判定

尚未进入 Feasible 区域时，每次 observation 更新距离趋势并累计连续证据：

- 距离总体减小：正常接近，继续 Phase；
- 距离持续增大或持续没有明显减小：均为 Phase 异常；
- 远离（away）和停滞（stall）统一计入同一个连续异常计数；
- 只有出现“距离总体减小”的正常接近时才清零；
- 连续 `evidence_updates` 次异常即返回对应的 `PHASE_ERROR`。

Phase 的结束与异常条件为：

- 当前 observation 首次满足 Feasible：Phase 正常结束，进入 Feasible 阶段；
- 尚未满足 Feasible 时发生夹爪状态改变：`PHASE_ERROR`，原因为过早改变夹爪状态。

同一 observation 同时检测到 Feasible 和夹爪状态改变时，先判定 Feasible entry，使该事件归入 Feasible 阶段，不把采样边界误判成 Phase Error。Phase 不再负责判断状态改变时的位置是否 Feasible。

#### 超参数边界

Stage 3 不新增超参数，而是复用原版已有的距离容差和连续证据次数。原版对应参数为：

- Phase：`wrong_way_tolerance_px`、`wrong_way_updates`；
- Feasible：`progress_tolerance_px`、`evidence_updates`，已经同时用于远离和停滞。

3D Phase 将它们统一为相同概念：

- `progress_tolerance_m`：把原像素距离容差改为米制对称 deadband；
- `evidence_updates`：沿用原来的连续证据次数。

每次更新计算：

```text
progress = previous_distance - current_distance
```

- `progress > progress_tolerance_m`：接近目标，清空所有异常累计；
- `progress < -progress_tolerance_m`：累计一次远离证据，同时累计一次异常；
- 其余情况：累计一次停滞证据，同时累计一次异常；
- 异常累计连续达到 `evidence_updates`：返回对应 `PHASE_ERROR`（away 或 stall）。

第一版不为远离和停滞分别增加阈值，也不测试 confidence。

##### 参数如何确定

两个参数的来源不同：

- `progress_tolerance_m`：原值是像素单位，不能直接换算成米。使用 `tests/phase3/` 从 `t=0` 完整回放 training demo，并在每个 Pick SkillStep 实际激活到 Feasible entry 的区间内，对正确目标和其他候选物体计算逐次 3D progress；在候选米制容差中，选择不会让成功轨迹中的正确目标误触发远离/停滞，同时仍能区分其他候选物体的最小值；
- `evidence_updates`：不重新学习，第一版沿用原 Feasible 的默认值 `2`。原因是新的 Phase 接管了原 Feasible 中“持续远离/持续停滞”的职责；`tests/phase3/` 只验证该值，不自动调参。

因此 Stage 3 实际只重新确定 `progress_tolerance_m`；如果 `evidence_updates=2` 无法通过 training trajectory 测试，再单独讨论是否修改。

以下内容不属于 Phase 3D 新增超参数：

- Feasible 区域：由 Feasible/Memory 定义，Phase 只将首次进入该区域作为正常结束条件；
- 夹爪状态改变：若 observation 已提供离散 gripper state，则只是事件，不需要阈值；若从连续 `gripper_qpos` 推导，阈值属于 observation preprocessing；
- 目标 3D 代表点：第一版使用逐坐标 median，不需要调参；
- 候选物体数量：只属于 `tests/phase3/` 的测试配置，不进入 runtime Phase 判定；
- template matcher 的已有参数：属于目标定位，不属于 Phase 趋势参数。

#### 第一步：修改 Memory System 判定

- 将 Stage 1/2 已验证的 metric depth、相机参数和反投影逻辑放入正式 `memory_system`，原测试直接测试正式实现，不从 runtime import test harness；
- 扩展 `VerifierObservation`，提供 Main metric depth 和完成反投影所需的相机参数；
- Phase matcher 返回匹配位置、尺度和变换后的当前目标 mask；
- `phase.py` 根据目标 mask 构建 3D 代表点，并持续维护距离趋势与连续证据；
- Execution Monitor 不再在第一次正向 progress 后退出 Phase，而是在首次 Feasible entry 时切换到 Feasible 阶段；
- Feasible 只提供当前位置是否属于 ready region，远离和停滞由 Phase 判断；
- Phase 内发生夹爪状态改变直接触发过早操作错误；Feasible 阶段如何处理后续状态改变在 Stage 4 中定义，Completion 只判断状态改变后的 skill 是否真正完成。

#### 第二步：`tests/phase3/`

目的：判断 training demo 中的 Pick approach 是否能在 3D 中与其他物体区分。

测试方式：

1. 每条 LIBERO-10 原始 training demo 都从全局 `t=0` 开始完整回放，不从 `segment.start` 直接初始化测试；
2. Execution Monitor 从 `t=0` 启动。第一步的 Phase 从 `t=0` 生效；后续 Pick Phase 在前一个 SkillStep 完成、当前 SkillStep 激活时生效。manifest 的 `segment.start` 只作为 Test Oracle 对齐，不作为 demo 回放起点；
3. 对每个生效的 Pick Phase，测试区间从 Phase 激活时刻到标注的首次 Feasible entry（`ready_frame`）；
4. 候选集合包含 `arguments.item` 和同一 task 中固定选择的若干个、可由 Memory 定位的其他物体；
5. 每个候选都使用相同的 `template match -> mask -> RGB-D -> representative XYZ` 路径；
6. 记录每个候选的距离序列，并计算累计接近量：

```text
approach(object) = distance_at_phase_activation - distance_at_feasible_entry
```

7. 正确目标的累计接近量应在候选中排名第一；
8. 成功 demo 在当前 Phase 激活后、首次 Feasible entry 前不应发生夹爪状态改变。

测试只输出 task、Pick step、正确目标、候选物体、累计接近量、排名和是否发生过早夹爪状态改变。Simulator object state、predicate 和 segmentation 只用于确定测试 Oracle，不进入被测试的 Phase 路径。

### Phase 3D Runtime 实现状态（当前进度）

已新增正式 runtime 实现：

- 新增 `memory_system/execute/phase3d.py`，实现 `Phase3DVerifier`；
- 复用 `PhaseVerifier.match_current()` 做目标模板匹配；
- 使用 `VerifierObservation.main_depth` / `camera_params` 计算 3D 距离；
- 维护 away / stall 合并的连续异常证据（只有正常接近才清零）；
- 在线 phase 检查默认每 8 个环境 step 一次（在 16 步 action chunk 的边界和中间点各检查一次）；
- 通过内部 `FeasibleVerifier` 判断 Feasible entry，进入后返回 `PHASE_DONE`；
- `ExecutionMonitor` 支持 `PHASE_DONE`，Phase 结束后进入 Feasible 阶段；
- 增加 `enable_phase_3d` 配置，`scripts/run_libero10_robotinit_20.sh` 默认 `COSMOS_PHASE_3D=1`；
- `Close` 默认不启用 Phase 3D 纠正。

当前已知 runtime 现象：

- `initstate_265` 5 episode 测试中，Phase 3D 已触发 `PHASE_ERROR` 和 recovery；
- 但 episode 仍可能失败，说明 Phase3D 的误报/纠正参数还需要继续调优；
- 该部分属于 runtime 实现状态记录，不是 `tests/phase3` 的测试结果。

当前 Phase 阶段尚未解决的问题：

- 无法解决“已经快速把东西抓取了”的情况；
- 也就是说，如果策略在 Phase 判定/纠正介入前已经快速完成抓取，Phase 3D 目前不能把该状态拉回来继续按原 Phase 流程处理。

### Stage 4：Feasible 3D

当前状态：已实现第一版实验，但效果不如 2D。当前决定保持 2D Feasible 为默认，不启用 3D Feasible，优先推进 Skill Completion 3D。

#### 实现内容

- 新增 `memory_system/execute/feasible3d.py`：`Feasible3DVerifier` + `ReadyDistance3DMemory`；
- 新增 `memory_system/offline/build_ready3d.py`：生成 `ready3d_targets.pt`；
- 新增 `scripts/check_ready3d_memory.py`：检查 3D ready memory 与 2D ready memory 的关键字段一致性；
- 新增 `enable_feasible_3d` / `COSMOS_FEASIBLE_3D` 开关，默认 `0`；
- 现有 2D `FeasibleVerifier` 完整保留，可随时切回。

#### 数据检查结果

- `ready3d_targets.pt` 共 350 个 prototypes；
- 与 2D ready entries 完全匹配：350/350，`ready_frame mismatch = 0`；
- 每个 phase 至少有 2 个 demo，无重复；
- `distance_m` 分布合理，未发现明显异常值。

#### 实验现象

- 3D Phase + 2D Feasible + Recovery 在 `KITCHEN_SCENE4` initstate_274 的 20-pair 测试中成功率 19/20（95%）；
  - `PHASE_ERROR = 0`；
  - `NOT_FEASIBLE = 21`；
  - `FEASIBLE RECOVERY = 21`；
  - 说明 Phase3D 配合原有 2D Feasible 表现良好；
- 3D Phase + 3D Feasible + Recovery 在相同任务 5-pair 测试中成功率 1/5；
  - 3D Feasible 实验中出现较多 `PHASE_ERROR`、`wrist_not_ready` 和 `feasible_error` 循环；
- Phase3D 内部 Feasible 与外层 Feasible3D 的 wrist 条件不一致：
  - Phase3D 内部 Feasible3D 未启用 wrist 检查；
  - 外层 Feasible3D 因 recovery 配置启用了 wrist 检查；
  - 导致 Phase 已判定 `PHASE_DONE`，外层却报 `wrist_not_ready` / `feasible_error`，形成循环；
- Feasible3D 进入后对 `persistent_reversal` / `persistent_stagnation` 过于敏感，recovery limit 达到后容易卡死。

#### 结论

- 3D Feasible 当前不作为默认路径，继续保留 2D Feasible；
- 3D Phase + 2D Feasible 是当前推荐组合；
- 后续若继续推进 3D Feasible，需要先解决：
  1. Phase3D 内部 Feasible 与外层 Feasible3D 的 wrist 条件一致性；
  2. Feasible3D 进入后的 drift/reversal/stagnation 处理；
  3. 3D Feasible 实验中的 recovery 循环问题；
- 当前重点转向 Stage 5：Skill Completion 3D。

### Stage 5：Skill Completion 3D

当前状态：下一阶段重点（开始 Skill 结束逻辑判定）。

目的：分别检验 3D 信息是否能改善各类 skill 的完成判断。

测试必须按 skill 和实际操作对象组织：

- Pick：覆盖 LIBERO-10 中所有不同抓取对象，由 simulator 判断是否真正抓取并完成；
- PlaceOn/PlaceIn：覆盖不同 item 和 target，由对应 simulator predicate 判断；
- Open/Close/Turn：覆盖相应目标，由 simulator joint state 或 predicate 判断。

不同 skill 使用什么 3D 信息，在各自阶段开始前单独讨论，不预先统一。

### Stage 6：3D Recovery/Correction

目的：检验 3D 信息是否能帮助系统从明确的错误状态恢复，并继续完成当前 skill。

测试应从受控错误状态开始，只判断纠正后是否回到目标阶段并完成对应 skill。Recovery 的目标表示、控制方式和测试条件在进入本阶段前单独讨论。

## 5. 测试组织原则

- 共享 LIBERO 环境启动、demo state 恢复和结果记录代码；
- 每个被测试模块拥有与自身功能直接对应的测试程序；
- 覆盖单位是 `task × skill step × item/target`，不能只报告任务总数；
- 正例和必要的反例由该模块的测试目的决定，不额外扩展测试范围；
- 测试输出以明确的预测、Oracle 和差异为主；可视化只用于定位错误；
- 每完成一个阶段，保留实现、对应测试和简短结果，再决定下一阶段。
